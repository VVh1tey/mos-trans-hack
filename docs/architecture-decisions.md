# Рабочее решение для хакатона

Схемы: [online-architecture.drawio](online-architecture.drawio), [training-architecture.drawio](training-architecture.drawio), [sequence.drawio](sequence.drawio). Открываются в diagrams.net / draw.io.

Дополнительные возможности и условия их включения: [optional-features.md](optional-features.md).

## Что именно прогнозируем

Для каждой точки `(tr_id, T)` предсказываем `target_delay_s` в секундах на **заданной** остановке `target_stop_id`, плановое прибытие на которую лежит в `(T+10 мин, T+15 мин]`. Знак важен: положительный означает опоздание. Для сабмита нужен ровно `sample_id;prediction`. Вероятность и цвет риска нужны приложению, но не заменяют числовой прогноз.

## Выбранный стек

| Часть | Технология | Причина |
|---|---|---|
| Подготовка данных и модель | Python 3.12, Polars/Pandas, CatBoost | Быстрый сильный baseline на небольших табличных данных; оптимизация MAE |
| Эксперимент с последовательностями | PyTorch, небольшой GRU/TCN | Выполнение требования стека и проверка, даёт ли история GPS прирост относительно CatBoost |
| Backend | Python 3.12, FastAPI, asyncio TCP server | NDTP-приёмник, API, Swagger, SSE, оркестрация |
| ML-сервис | отдельный Python/FastAPI контейнер | Явная граница backend/ML и независимый инференс |
| События и оперативное состояние | Redis Streams, Redis Hash/Sorted Set с TTL | Разделение приёма и обработки, повторная доставка, быстрый доступ к окнам по ТС |
| Долговременное хранение | PostgreSQL | Расписание, соответствия устройств, история прогнозов и инцидентов |
| Архив телеметрии | CSV/Parquet на постоянном volume | Replay, обучение и аудит без постоянного роста Redis |
| Эксперименты и модели | Отдельные папки `runs/<run_id>/`, манифесты и CSV-индекс | Сравнение MAE и перенос воспроизводимых запусков |
| Наблюдаемость | Prometheus + Grafana | Метрики обработки, ресурсов и история прогнозов на готовом дашборде |
| Дашборд | React, TypeScript, Vite, MapLibre GL JS | Карта, быстрые обновления, ясная диспетчерская UI |
| Сборка | Docker Compose | Подъём всех трёх модулей одной командой |

Kafka, Kubernetes, PostGIS и ONNX добавлять только при измеренной необходимости: они не повышают балл за рабочий MVP сами по себе.

## Redis: события и фичи

### Три независимых такта онлайн-работы

1. **Каждый пакет, примерно раз в 12–15 секунд на ТС в данном датасете:** NDTP listener проверяет и пишет нормализованное событие в Redis Stream. Feature worker обновляет короткое состояние ТС и агрегаты. Это дешёвая операция; ML-модель не вызывается.
2. **Каждые 30 секунд на активное ТС (настраиваемо):** scheduler выбирает момент прогноза `T`, находит первую плановую остановку с временем в `(T+10 мин, T+15 мин]`, читает согласованный снимок признаков с `event_time ≤ T` и вызывает ML-сервис. Если такой остановки нет, прогноза в этот тик нет. Для неизменившегося состояния можно переиспользовать предыдущий прогноз, но время и свежесть данных должны отображаться честно.
3. **После нового прогноза или смены состояния:** обновить один актуальный прогноз по ключу `(tr_id, target_stop_id)`, сравнить с прошлым риском, создать/обновить один алерт и отправить изменение через SSE. Браузер не опрашивает модель и не считает фичи.

Пример: остановка по плану в 12:15. В 12:00 она впервые входит в окно прогноза; модель выдаёт задержку и расчётное прибытие. В 12:00:30…12:04:30 прогноз можно обновлять на свежих пакетах. В 12:05 плановая остановка выходит из окна 10–15 минут, новые прогнозы для неё прекращаются; карточка остаётся как ранее выданное предупреждение до прибытия или закрытия. Это соответствует правилу датасета, где горизонт определяется **плановым** временем целевой остановки.

Используются два времени: `event_time` из устройства определяет допустимые данные для признаков, а время обработки определяет свежесть и latency. Если пакет пришёл поздно, он не должен превращаться в «прогноз задним числом». При отсутствии новых пакетов scheduler помечает состояние stale и не выдаёт его за свежий ML-прогноз. Обработка пакетов и периодический scheduler работают независимо; Redis хранит последние окна и текущий снимок.

NDTP listener валидирует пакет, нормализует его и записывает событие в Redis Stream `telemetry`. Группа `feature-workers` читает события через `XREADGROUP`, обновляет состояние и подтверждает событие `XACK` только после успешной обработки. Предикт сохраняется в актуальный снимок ТС и публикуется как событие `prediction.updated`; backend передаёт обновления браузеру через SSE. Для истории и повторной обработки Streams обрезаются по согласованному retention, а долговременный CSV/Parquet архив хранится отдельно.

Фичи считаются инкрементально по `tr_id`: короткое окно GPS-точек (например, Redis Sorted Set по `event_time`), последнее состояние (Hash), rolling-суммы и счётчики для окон 1/3/5 минут. При дубле используем `packet_id`/составной event key, при опоздавшем пакете пересчитываем затронутое окно либо игнорируем его по зафиксированному допустимому лагу. Для одного ТС важен порядок; простой общий consumer group с несколькими воркерами его не гарантирует. При горизонтальном масштабировании шардируем потоки по `hash(tr_id) % N`, закрепляя каждый шард за одним обработчиком, либо используем другой механизм последовательной обработки по ключу.

Redis хранит временное состояние, но не является единственным источником истории обучения. Периодически сохраняем нормализованные события и расписание в файлы/БД; при рестарте восстанавливаем состояние из снимка и хвоста Stream. Мониторим длину Streams, pending-сообщения, возраст последнего пакета и latency от `event_time` до предикта.

## PostgreSQL и архив

PostgreSQL — постоянное хранилище справочников и результатов: `vehicles`/`unit_mapping`, `stops`, `schedule_plan`, `predictions`, `alerts`, при необходимости `actual_arrivals`. В `predictions` пишем момент `T`, целевую остановку, числовой прогноз, риск, версию модели и время обработки; в `alerts` — открытие, обновления, закрытие и статус. Это позволяет после рестарта восстановить экран и считать исторические метрики. Эксперименты и веса моделей хранятся отдельно в `runs/`.

Сырые пакеты идут в Redis Stream с ограниченным retention. Отдельная группа `archive-workers` сохраняет нормализованную телеметрию батчами в Parquet/CSV на постоянном volume; для хакатона существующие CSV уже служат историческим архивом. Не писать каждый GPS-пакет синхронно в PostgreSQL на пути к предикту. Если позже нужен SQL по всей телеметрии, добавить партиционированную по дате таблицу и пакетную загрузку. Redis AOF уменьшает потери при рестарте, но не заменяет архив и резервную копию PostgreSQL.

## Наблюдаемость: Prometheus и Grafana

В полном режиме Compose добавляются два сервиса: Prometheus собирает `/metrics` у Backend API, NDTP ingest, feature worker/scheduler и ML inference; Grafana получает агрегированные метрики из Prometheus и историю отдельных прогнозов из PostgreSQL. Конфигурации источников и JSON дашборда хранятся в репозитории и автоматически подхватываются при старте Grafana. Участник открывает готовый экран без ручного создания панелей.

Минимальный экран «Здоровье прогноза» содержит: (1) активные ТС и время последнего пакета, (2) входящие пакеты/с и ошибки NDTP, (3) лаг Redis Stream и pending, (4) p50/p95 полного пути пакет→прогноз и отдельно ML-инференса, (5) число прогнозов и алертов по риску, (6) CPU и RAM процессов Backend/worker/ML, (7) последние прогнозы из PostgreSQL с `T`, ТС, остановкой, задержкой, моделью и статусом, (8) MAE по накопившимся фактам, если они уже появились. Пока фактов нет, панель MAE явно показывает «нет данных», не ноль.

Для p95 используем histogram в секундах с фиксированными корзинами вокруг цели 1–2 с. Метки только низкой кардинальности (`service`, `status`, `model_version`, `risk`); `tr_id`, `sample_id` и `packet_id` остаются в PostgreSQL и не становятся Prometheus labels. Python-клиент даёт метрики процесса, включая CPU time и RSS; измерение ресурсов именно контейнеров через cAdvisor можно добавить отдельным профилем на совместимом Linux Docker-хосте. Это сохраняет базовый запуск на машинах команды простым.

Grafana — операционный/технический дашборд для команды и жюри; React + Mantine + MapLibre остаётся рабочим экраном диспетчера. История прогнозов в Grafana читается из PostgreSQL, потому что Prometheus хранит временные ряды и агрегаты, а не строки отдельных предсказаний.

## Эксперименты и жизненный цикл модели

Каждый запуск создаёт `runs/<run_id>/` с манифестом, хешами входных CSV и кода, MAE на test и артефактом модели. `compare.py` пересоздаёт CSV-индекс; сравнение корректно для одинакового отпечатка данных. Для финального `submission.csv` отдельно сохраняем команду генерации и проверку покрытия `sample_id`. Онлайн-сервис читает выбранную через `select.py` совместимую модель; откат — выбор предыдущего запуска.

Обучение запускается отдельным Compose без PostgreSQL и онлайн-сервисов. Команда передаёт папки запусков через общее хранилище и сравнивает их по одному тестовому протоколу. Учить модель на новых событиях можно после появления фактической задержки целевой остановки: до этого у них нет target.

GPU используем там, где есть измеримый смысл: PyTorch эксперимент обучается на CUDA при наличии устройства, CatBoost можно сравнить с `task_type="GPU"`. Онлайн CatBoost обычно сначала оставляем на CPU и измеряем p50/p95 latency и throughput; GPU-инференс нужен только при подтверждённом узком месте. Масштабируемость инференса обеспечивается отдельными stateless репликами ML-сервиса с одной закреплённой версией модели, а состояние окон остаётся в Redis.

## Модель и признаки

1. Зафиксировать baseline `prediction = cur_dev_s`; измерить MAE на `labels_test.csv`.
2. Обучить `CatBoostRegressor(loss_function="MAE")`. Признаки только из информации на момент `T`: `cur_dev_s`, время до целевой остановки, последние GPS/скорость/курс, скользящие скорость и доля стоянки за 1/3/5 минут, расстояние по прямой до остановки, прогресс по цепочке остановок, время суток и день недели, качество/давность последней точки.
3. Разделять данные по периоду и ТС, контролировать сильную зависимость соседних прогнозных точек. `train` для обучения, `test` для честной локальной проверки, `validate` только для финального CSV. Не использовать `time_fact_begin` целевой или будущих остановок как признак.
4. PyTorch модель учить на последовательности последних N телематических точек и сравнить MAE. Включать в финальный ансамбль только при улучшении на holdout. Если прироста нет, PyTorch остаётся отдельным воспроизводимым экспериментом, а инференс использует CatBoost.
5. Для дашборда риск можно вычислять отдельным классификатором `P(target_delay_s > 120)` либо калибровать по остаткам регрессии. Порог +120 с взят из `target_class` датасета; пороги цветов необходимо сверить с диспетчерским сценарием.

Причину показывать как **вероятную**: «низкая скорость», «долгая стоянка», «уже есть отклонение», «нет свежей телеметрии». В данных нет подтверждённой причины и нет колонки двери; нельзя выдавать эти объяснения за факт.

## Онлайн-контур

Эмулятор подключается к TCP listener backend. Listener проверяет длину кадра и CRC, принимает handshake и `G6CellNav00`, нормализует в те же поля, что `traffic.csv`. Связь `unit_id → tr_id` готовится из исторической таблицы; для неизвестного устройства показывается «без привязки», без выдуманного прогноза. Feature worker читает Redis Stream и обновляет последнее состояние ТС и короткую историю в Redis. Отдельный scheduler по своему таймеру получает план остановок, собирает признаки из этого состояния и вызывает ML-сервис, когда целевая остановка входит в окно 10–15 минут. Ответ хранит время расчёта, версию модели, целевую остановку, прогноз и риск.

Алерт создавать только если до **планового** прибытия 10–15 минут; повторные прогнозы обновляют одну карточку. При обрыве потока сохранять последнее состояние с явной меткой «нет новых данных с …», а затем переходить на историческую оценку с пониженной уверенностью. Это демонстрирует деградацию без ложного ощущения живого прогноза.

В `traffic.csv` нет `route_id` и геометрии линии. `tr_id` обозначает ТС, у которого расписание на весь день с повторяющимися остановками. Для карты MVP можно показать точки ТС, фактический GPS-трек и приближённую линию ближайших остановок конкретного рейса; длинные разрывы в расписании разрывают линию. Точный map matching требует отдельной геометрии дорожной/маршрутной сети.

## Экран диспетчера

Пользователи: диспетчер всей сети и диспетчер отдельной линии/маршрута. Один React-интерфейс поддерживает иерархию **сеть → линия/маршрут → ТС/инцидент**. Выбранный уровень и фильтры отражаются в URL, чтобы открыть ту же картину по ссылке. Переключатель уровня всегда доступен в верхней панели; смена уровня сохраняет период и выбранный риск.

**Обзор сети:** карта всех активных ТС с цветовым риском и группировкой маркеров при отдалении; сверху число активных ТС, красных рисков, проблемных линий и время последнего пакета. Рядом список линий/маршрутов по срочности и лента критичных алертов. Клик по линии переводит в её рабочий вид; клик по алерту фокусирует ТС.

**Линия/маршрут:** карта приближённой или официальной геометрии выбранной линии, все её ТС, остановки и выделенный проблемный участок. Верхние показатели относятся только к выбранной линии: активные ТС, средний прогноз отклонения, число алертов, свежесть данных. Список ТС отсортирован по риску и времени до целевой остановки. Клик раскрывает карточку с ТС, адресом остановки, прогнозом в секундах, вероятностью, предполагаемым фактором, свежестью GPS и трендом скорости. Возврат к сети — один явный элемент навигации.

**Источник route_id:** в текущих CSV нет официального номера маршрута и связи ТС→маршрут. При появлении справочника (`route_id`, название, геометрия/остановки, привязка ТС во времени) фильтр работает по нему. Для демо без справочника допускается вычисленный `route_group_id` из повторяющейся последовательности остановок; в интерфейсе он называется «восстановленная линия», и `tr_id` не выдаётся за официальный маршрут. Все агрегаты сети/линии вычисляются по одинаковым правилам на backend. Фильтры: риск, статус связи, линия, ТС, остановка. SSE обновляет текущий срез без сброса выбранного уровня.

## План Docker Compose для команды

Репозиторий использует два независимых файла: корневой `compose.yaml` для долгоживущего онлайн-контура и `compose.train.yaml` для одноразового обучения. Training job создаёт папку в `runs/`, а ML-сервис читает `runs/selected.json` или использует fallback. Онлайн Compose включает инфраструктуру и отдельные процессы из схемы; ingest, feature worker, scheduler и archive worker пока заглушки. Таблица ниже описывает целевое поведение после реализации рабочих модулей.

| Сценарий | Что запускается | Что получает участник |
|---|---|---|
| Обучение | Одноразовый training job и локальные папки `dataset/`, `runs/` | Команда запускает обучение, видит MAE в `runs/index.csv` и сохраняет артефакт модели |
| Полная система | PostgreSQL, Redis, NDTP ingest, feature worker/scheduler, ML inference API, Backend API, React dashboard, Prometheus, Grafana, эмулятор или replay | Участник выбирает совместимую модель, запускает поток и видит позиции, прогнозы, алерты и технические метрики на двух экранах |

Модель выбирается командой `select.py <run_id>` и копируется в `runs/selected.json`. ML-сервис сообщает имя модели в health check и каждом прогнозе. Для первого Compose достаточно выбрать модель и пересоздать ML-сервис. Пока модель не обучена, сервис использует fallback.

Датасет монтируется только на чтение для обучения, `runs/` — на запись в training job и только на чтение для ML-сервиса. PostgreSQL и Redis имеют постоянные volumes; веб-интерфейсы открываются на документированных портах. Инициализация схемы БД, health checks и порядок старта сервисов уже входят в Compose. Replay по историческому времени предстоит реализовать.

README содержит команды старта, обучения и выбора модели и адреса панели, API, Prometheus и Grafana. Сценарий первого реального алерта и p95 latency можно подтвердить после реализации обработки событий.

## Порядок реализации и проверки

1. Проверить baseline и валидный CSV-сабмит; затем улучшать MAE CatBoost.
2. Поднять все сервисы Compose и провести один пакет NDTP через парсер, feature builder, ML API и SSE до экрана.
3. Добавить карту и карточку, затем метрики latency, пропускной способности, reconnect и stale-состояния.
4. Сделать README с одной командой запуска, примером конфига эмулятора и шагами для жюри; приложить Swagger и документацию функций.

Ключевая проверка: один и тот же feature builder для офлайн-прогноза и онлайн-инференса, без чтения телеметрии после `T`.
